# Platform migration (KVox)

The Prisma schema is composed, not hand-written. `apps/api/prisma/schema/` is generated by `platform db compose` from the platform fragments plus `apps/api/prisma/fragments/*.prisma`. There is no `schema.prisma`. Run these from `apps/api`. Background: `docs/DEVELOPMENT.md` ("Making Database Changes"), `docs/platform-adoption/local-exceptions.md`, `docs/runbooks/database-baseline.md`.

Database work goes to the `database-dev` agent. The main agent does the git steps.

## What you may and may not touch

| Path | Rule |
|---|---|
| `apps/api/prisma/fragments/*.prisma` | Yours. KVox models and `extend model` blocks |
| `apps/api/prisma/schema/` | Generated and committed. Never hand-edit |
| `apps/api/prisma/migrations/` KVox directories | Yours, created by `prisma:migrate:dev` |
| `apps/api/prisma/migrations/` installed platform directories | Byte copies. Never edit or rename, comments included. The lock hashes the raw bytes |
| `apps/api/prisma/platform.lock` | Written by `db:sync` and `db:baseline`. Hand-edit only `rawSqlIndexes` and `deviations` |
| `apps/api/prisma/drift-allowlist.json` | Yours. See the allowlist rule |

KVox never authors platform migrations. There is no `db:promote` and no changeset for one. A change to a platform table is a request to the platform repository. Until it ships, the local workaround is a side table or a declared deviation, listed in `local-exceptions.md`.

## A. Change a KVox table

1. Edit the fragment of the domain in `apps/api/prisma/fragments/` (`transcripts`, `notes`, `search`, `graph`, `ask`).
2. `npm run db:compose`.
3. `npm run prisma:migrate:dev -- --name <snake_case_name>`.
4. `npm run prisma:generate`.
5. Run the checks below. Commit the fragment, `prisma/schema/` and the new migration together.

Rules:

- A relation to a platform model needs a back-relation: `extend model User { ... }`, `extend model StorageObject { ... }` or `extend model Job { ... }`, in the fragment that owns the foreign key. Keep the `@relation("...")` names.
- An `extend` block holds back-relation fields only. A scalar field, an owning relation or a block attribute is refused (`EXTEND_SCALAR_FIELD`, `EXTEND_OWNING_RELATION`, `EXTEND_BLOCK_ATTRIBUTE`). `NOT_EXTENSIBLE` means: use a side table keyed by the platform id.
- At most one open PR may carry a migration. A second one rebases and regenerates, so its timestamp is newer.
- A new job type needs no migration. `jobs.type` is a plain string.

## B. Take a new platform release

1. Bump `@marinoscar/platform-db` to the exact version in `apps/api/package.json`, then `npm install`.
2. `npm run db:sync`. It installs the missing platform migrations as byte copies after KVox's own.
3. Read each new directory under `apps/api/prisma/migrations/`. Check for `ALTER` on a table KVox extends and for role or permission data changes.
4. `npm run db:compose` (the platform fragments may have changed), then `npm run prisma:generate` and fix compile errors. Mark each workaround as a shim (see below).
5. `npm run prisma:migrate`, then the checks below.
6. Commit the new directories and `platform.lock` together. A rename or an edit of an installed directory makes `db:check` fail with `LOCAL_MODIFIED`.

## C. The raw-SQL list rule

Prisma cannot express partial indexes, expression indexes, trigram, HNSW or GiST indexes, generated `tsvector` columns, `tstzrange` columns, CHECK constraints or the evidence triggers. They live only in `migration.sql`. That is intentional drift (`AGENTS.md`, "Invariants that are easy to break").

- Never add `@@unique` or `@@index` for one, and never replace one with a `findFirst` before the insert.
- Every KVox partial or expression index goes under `rawSqlIndexes` in `platform.lock` as `{ name, definition }`. Copy `definition` exactly from a migrated dev database: `SELECT indexdef FROM pg_indexes WHERE indexname = '<name>';`
- The drift test asserts the list against `pg_indexes`. A missing or reworded entry fails with `INDEX_MISSING` or `INDEX_DEFINITION_DIFFERS`.

## D. The drift-allowlist rule

`npm run db:drift:kvox` runs `platform db drift`, removes the statements in `apps/api/prisma/drift-allowlist.json`, and fails on anything left.

- Each entry is `{ statement, reason, removeIn }`. `removeIn` is an issue number. `apps/api/test/prisma/drift-allowlist.spec.ts` fails without it.
- An entry is for a statement Prisma prints because its schema language cannot declare the object (the GIN, GiST and HNSW indexes, generated columns), or for a declared deviation column.
- Never add an entry to hide a real difference on a platform table. Fix the cause. If `SCHEMA_DRIFT` names SQL that is in the schema but in no migration, add the migration.
- The PR that closes an entry's `removeIn` issue deletes the entry.

## E. Shims and deviations

- A temporary workaround in code carries `// PLATFORM-ADOPTION-SHIM(<issue that removes it>)` and a row in `docs/platform-adoption/local-exceptions.md`.
- A column KVox adds to a platform table is a deviation in `platform.lock`, a `DROP COLUMN` entry in the drift allowlist and a row in `local-exceptions.md`. Avoid it. Use a side table.
- The baseline of an existing database is a one-off operator action (`docs/runbooks/database-baseline.md`). Never run `db:baseline --apply` from `kvox deploy update`.
- KVox runs as superuser until #471. Do not change `POSTGRES_USER`. `CREATE EXTENSION vector` needs it.

## Check before you commit

```bash
cd apps/api
npm run db:compose:check   # prisma/schema/ equals a fresh compose
npm run db:check           # installed SQL equals the package, lock is consistent
npm run db:drift:kvox      # replayed migrations equal the schema (needs a shadow database)
npm run typecheck && npm test
npm run test:db            # when the change touches queries or constraints
```

Flag the change for the docs agent: table inventory in `docs/ARCHITECTURE.md`, and `local-exceptions.md` if a shim changed.
