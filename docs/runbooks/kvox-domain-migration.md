# Runbook: author a domain migration (`@marinoscar/kvox-db`)

Use this to change a domain table, column or index (transcripts, notes, search, graph, ask), to install the domain into a new host, or to recover when `kvox-db check` fails. The package is `packages/kvox-db` ([README](../../packages/kvox-db/README.md)); the platform side of the schema is the [platform-migration skill](../../.claude/skills/platform-migration/SKILL.md).

## The two copies

The domain's fragments and migrations live in the package. The app holds installed copies that `kvox-db sync` writes:

| In the package | In the app (`apps/api/prisma/`) | Rule |
|---|---|---|
| `schema/kvox.<slice>.prisma` | `fragments/kvox.<slice>.prisma` | Generated, header `GENERATED by kvox-db sync`. Never edit, never `prisma format`. |
| `migrations/<id>/migration.sql` | `migrations/<id>/migration.sql` | Byte-identical, comments included. Never edit, never rename. |
| `migrations/manifest.json` | `kvox.lock` | The manifest hashes the package copy, the lock hashes the installed copy. |
| `raw-sql-indexes.json` | `platform.lock` `rawSqlIndexes` | Merged by `sync`; `platform db drift` asserts them against `pg_indexes`. |

`apps/api/prisma/fragments/` also holds the web edition's own side tables (`allowlist-reminders.prisma`, `object-ownership.prisma`). Those are the app's and are edited in place.

## Change a domain table

Run from `apps/api` unless noted. At most one open pull request may carry a migration; a second rebases and regenerates so its timestamp is newer.

1. **Edit the fragment in the package**, `packages/kvox-db/schema/kvox.<slice>.prisma`. Keep every block comment. A relation to `User`, `StorageObject` or `Job` needs its back-relation in an `extend model` block of the same fragment.
2. `npm run db:compose`. It runs `kvox-db sync` (the generated fragment copy updates) and then `platform db compose` (`prisma/schema/` updates).
3. `npm run prisma:migrate:dev -- --create-only --name <snake_case_name>`. This writes `prisma/migrations/<timestamp>_<name>/migration.sql` without applying it.
4. **Review the SQL.** Hand-write what Prisma cannot express: partial unique indexes, expression indexes, GIN/GiST/HNSW/trigram indexes, generated columns, `tstzrange` columns, CHECK constraints, triggers. Edit `migration.sql` now; after step 5 it is frozen. A migration may only touch domain tables; the only thing it may do to a host table is declare a foreign key to `users`, `organizations`, `storage_objects` or `jobs` (`ADD CONSTRAINT ... REFERENCES`).
5. `npx kvox-db promote <timestamp>_<name> --id <name> --slice <slice>`. It refuses a migration that touches a table the domain does not own, copies the file into `packages/kvox-db/migrations/<timestamp>_<name>/`, appends it to `manifest.json` (hash, slice, `requiresHostTables`) and installs it into the app under the same name, updating `prisma/kvox.lock` and `platform.lock` `appMigrations`.
6. **List any new special index.** If the migration created a partial, expression, GIN, GiST, HNSW or trigram index, `promote` prints its name. After applying the migration (step 7), copy its definition: `SELECT indexdef FROM pg_indexes WHERE indexname = '<name>';`, add `{ name, table, definition }` to `packages/kvox-db/raw-sql-indexes.json` (sorted by name), and run `npx kvox-db sync` so `platform.lock` gets it. New generated columns, CHECK constraints, functions and triggers go in `schema-objects.json`. Add a drift-allowlist entry only for a statement Prisma prints because it cannot declare the object (see the platform-migration skill, section D).
7. `npm run prisma:migrate` (or `prisma:migrate:dev`) to apply, then `npm run prisma:generate`.
8. Check:

   ```bash
   npm run db:compose:check     # prisma/schema/ equals a fresh compose
   npm run db:check             # platform check, then kvox-db check (byte identity)
   npm run db:drift:kvox        # replayed migrations equal the schema (needs a shadow database)
   npm run db:kvox:check:database   # extensions, raw indexes, triggers in the dev database
   npm run test:kvox-packages   # manifest hashes and the raw-SQL index tripwire
   ```

9. Commit together: the package copy (`packages/kvox-db/schema`, `migrations`, inventories), the app copy (`prisma/fragments`, `prisma/migrations`, `prisma/schema`), `prisma/kvox.lock`, `prisma/platform.lock` and a changeset (`npx changeset`, minor for `@marinoscar/kvox-db`).

Never fix a mistake by editing an installed migration: production databases hold its checksum in `_prisma_migrations`. Write a new migration.

## Install the domain into a new host

KVox Desktop and the bare host have no domain history, so they use `stable` names. They build `prisma/` from scratch, so the platform timestamp is pinned before the domain's September-2026 ids: the platform tables come first on a fresh database and the platform names are deterministic.

```bash
npx platform db sync --timestamp 2024-01-01T00:00:00Z && npx platform db compose   # platform schema and migrations first
npx kvox-db sync --names stable                    # fragments, migrations, kvox.lock
npx platform db compose
npx kvox-db check
```

As a PostgreSQL superuser, once per database: `CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS pg_trgm;`. `kvox-db` never creates an extension. Then apply with `prisma migrate deploy` and run `npx kvox-db check --database`.

## Migration folder names

Rule: an installed migration's folder name is a pure function of the migration; an upgrade only appends names, never renames one. A database records the name in `_prisma_migrations`, so a name that moves breaks it.

| `--names` | Installed name | Use |
|---|---|---|
| `original` | the package id (`20260914130000_add_transcripts`) | a host whose databases already ran the migrations under those names (the web app) |
| `stable` | `<the id's 14-digit timestamp>_kvox_<slug>` (`20260914130000_kvox_add_transcripts`) | a host with no domain history; the default there. Depends only on the package id, never on build time or other packages' migration counts |
| `after-host` | `<ts>_kvox_<slug>`, newest host directory + 1s | deprecated; kept only for a host that already installed under it |

`after-host` is deprecated because its names depend on the newest host directory. When a platform upgrade adds a migration to a host that builds `prisma/` from scratch, every domain name shifts, and databases that recorded the old names in `_prisma_migrations` break. A host with a `prisma/kvox.lock` keeps the policy the lock records.

Platform pin: a host that builds from scratch runs `platform db sync --timestamp 2024-01-01T00:00:00Z`, before the domain's September-2026 ids, so the platform migrations sort first and their names do not depend on the clock.

Upstream gap: `platform db sync` still derives names from the clock or `--timestamp` and the newest existing directory (`max(now, latest+1s)`). A host that keeps its `prisma/` between builds and one that rebuilds from scratch can therefore give a newly added platform migration different names. Tracked as a seam request: [marinoscar/EnterpriseAppBase#992](https://github.com/marinoscar/EnterpriseAppBase/issues/992).

## When a check fails

| Code | Meaning | Fix |
|---|---|---|
| `FRAGMENT_MODIFIED`, `FRAGMENT_MISSING`, `FRAGMENT_STALE` | a generated fragment copy differs from the package | `npx kvox-db sync`; edit the package file, not the copy |
| `INSTALLED_MODIFIED` | an installed `migration.sql` differs from `kvox.lock` (a comment counts) | restore it from version control |
| `LOCK_ENTRY_MISSING` | the lock names a directory that is gone | restore the directory; never reinstall one that may be applied |
| `NOT_INSTALLED`, `LOCK_MISSING` | the package has migrations the app has not installed | `npx kvox-db sync` |
| `PACKAGE_MIGRATION_MODIFIED` | a package migration differs from `manifest.json` | restore it; a published migration is never edited |
| `UNLISTED_RAW_INDEX`, `LISTED_INDEX_NOT_FOUND` | `raw-sql-indexes.json` and the migrations disagree | add or fix the inventory entry (step 6) |
| `FRAGMENT_DECLARES_RAW_INDEX` | a fragment declares `@@unique`, `@@index` or `@unique` for a raw-SQL index | remove the declaration; the index is intentional drift |
| `PLATFORM_LOCK_INDEX_MISSING` | `platform.lock` lacks a raw index | `npx kvox-db sync` |
| `EXTENSION_MISSING`, `INDEX_MISSING`, `TRIGGER_MISSING`, `GENERATED_COLUMN_MISSING` (with `--database`) | the database lacks an object | run the printed `CREATE EXTENSION` as a superuser, or apply the missing migration |

## Rollback

Revert the pull request. The installed migration copies never moved or changed, so a database is unaffected. To undo an adoption delete `prisma/kvox.lock` and the generated `prisma/fragments/kvox.*.prisma` and restore the fragments from version control.
